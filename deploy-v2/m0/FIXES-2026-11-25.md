# M0 fixes: fresh-estate build, 2026-11-25

Found while building a new 4-VM estate (`ditb-v1`) from `main` @ `9f1a9cd` with
`deploy-v2/m0/install.sh`. Before these fixes, a clean install could not pass
the M0 gate. After them, `install.sh` exited 0 with **all 5 M0 acceptance checks PASS**
(engine ×4, cross-VM publish, Go-SDK smoke, network matrix, decision log).

Each fix is independent and small. They are listed in the order a fresh install hits them.

---

## 1. `.gitignore` hides two assets that `install.sh` requires

**Symptom.** `install.sh --check-only` on a fresh clone:

```
check-only: missing assets (not a failure in check-only):
  deploy-v2/m0/go-sdk-smoke
  deploy-v2/m0/.env.example
```

A real run dies in `check_assets`.

**Root cause.** Two ignore rules match more than intended:

| Rule | Intended to ignore | Also ignores |
|---|---|---|
| `go-sdk-smoke` (line 12, "compiled Go binaries") | the built binary | the **source directory** `deploy-v2/m0/go-sdk-smoke/` |
| `.env.*` (line 3) | real secrets such as `.env.registry` | the **template** `deploy-v2/m0/.env.example` |

Both files were tracked under `deploy/m0/` (from `8d5101e`). They were deleted with
that tree in `392b104` ("Deploy Pass 2"). When they were moved to `deploy-v2/m0/`, git silently
skipped them because of the rules above.

**Fix.**
- `.gitignore`: ignore only the binary (`deploy-v2/m0/go-sdk-smoke/go-sdk-smoke`), and add
  `!.env.example` / `!**/.env.example` negations.
- Restore `deploy-v2/m0/go-sdk-smoke/{go.mod,go.sum,main.go}` and
  `deploy-v2/m0/.env.example` verbatim from `392b104^:deploy/m0/`. Content is unchanged;
  the `.env.example` comments still say `deploy/m0`, and are left for the owner to touch up.

**Verified.** `go build` succeeds. The M0 gate 3 Go-SDK workflow completed against Temporal on vm-xb:7233.

## 2. RabbitMQ crashes on first boot (`.erlang.cookie: eacces`)

**Symptom.** §3 fails with `FAIL: rabbitmq healthcheck flapping (memory alarm? see M0 §8)`.
The container has `Exited (1)` and its log says:

```
Error when reading /var/lib/rabbitmq/.erlang.cookie: eacces
```

**Root cause.** This is a race created by `install.sh` itself, not a memory or VM problem. The health-check
loop runs `docker exec <rabbitmq> rabbitmq-diagnostics -q ping` **as root** about 1s
after `compose up`. That CLI call creates `/var/lib/rabbitmq/.erlang.cookie` owned by
`root:root 0400` *before* the image entrypoint has chowned the data dir and dropped to
the `rabbitmq` user. The server then cannot read its own cookie and exits.

**Evidence** (`rabbitmq:4.3.7-management-alpine`, the repo's compose.yaml, throwaway project):

| Test | Result |
|---|---|
| A: `compose up`, no exec for 20s | healthy |
| B: `compose up`, immediate `exec` as root (current install.sh) | **crash, eacces** |
| C: `compose up`, immediate `exec -u rabbitmq` | healthy after 6s |

The 4.4.1 image (what the floating `4-management-alpine` tag resolved to on 2026-11-25)
behaves identically. **Pinning alone does not fix this.**

**Fix.** Add `-u rabbitmq` to all four `rabbitmq-diagnostics -q ping` calls in `install.sh`
(the coexistence-mode check and the §3 health loop).

**Recovery note.** A data volume that has already been poisoned keeps the root-owned
cookie. On a fresh estate, `docker compose down && docker volume rm
ea-m0-rabbitmq_rabbitmq-data` before re-running. Don't do this on an estate holding queue data.

## 3. Pin the RabbitMQ image by digest

**Why.** `compose.yaml` used the floating `rabbitmq:4-management-alpine` (its comment said
"pin exact tag in image-tags.env"). `image-tags.env` is only a record; compose never reads
it. The floating tag moved to 4.4.1 the day before this build. The M0 §0 rule is "record every
pin", so the running image should be the pinned one.

**Fix.**
- `compose.yaml`: `rabbitmq:4.3.7-management-alpine@sha256:70e84f027caee3c5f5d9f0fc8910de3e0f8d1e02a5972e170544fb504dc60935`
- The `install.sh` heredoc that writes `image-tags.env` records the same reference.

4.3.7 is the latest 4.3.x patch (released 2026-11-17). Bump it deliberately when needed.

## 4. Topology declare races the management plugin (curl exit 56)

**Symptom.** With fix 2 in place, §3 exits with code **56** immediately after
`assumed — declare topic exchange agent.tasks + ea-tasks queue + binding + DLQ`.

**Root cause.** `rabbitmq-diagnostics ping` succeeds about 2s before the management plugin
listens on :15672. `declare_topology` runs under `set -e` and its first `curl -XPUT` gets a
connection reset (curl 56), which aborts the script. The existing comment at the probe already
notes "empty (API not up yet on a fresh first boot)" but nothing waits for it.

**Fix.** At the top of `declare_topology`, poll `GET /api/overview` (up to 60s) until it
answers 2xx or 401, then probe and declare as before. If it never answers, `die`
with a clear message.

**Verified.** The re-run declared `agent.tasks` → `ea-tasks` (x-max-priority 3), `ea-tasks.dlq`,
`ea-tasks.response`. Gate 2 cross-VM publish from vm-xa over AMQP 5672 showed queue delta = +1.
